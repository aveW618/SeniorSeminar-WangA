# SeniorSeminar
A student project for Managing Scheduling and Optimizing a Solution that reduces conflicts

## Develop a Java Based Solution to Minimize Scheduling Conflicts

The attached CSV/Spreadsheet file is the result of sending out a google form and having students enter their top 5 ranked choices, using the mini table in the spreadsheet that contains the sessions, IDs and speakers.

**Feel free to clean up the spreadsheets, and even create new ones if needed, HOWEVER - you many not alter student preferences in the fiel or spreadsheet.

- 5 Time Slots 
- 5 Classrooms (16 students max/ class)
- Sessions Cannot Run more than Twice
- Notice that some sessions are taught by same person
- Student May Not Repeat a Session
- Schedule a Student for 5 Session

**Goal is to design and code an algorithm that generates a schedule for the students, given structure above, with the fewest number of conflicts

- Generate a schedule for the sessions and speakers, 
- Create lists for each student so they know what sessions to attend, rooms and times.

Update for May 17 (at-home):
Today I finished turning my senior seminar project from separate pieces of code into a complete program. A major part of today was figuring out how to organize the project better without making it feel like I had started over completely. Instead of how I originally organized my code (into 7-8 files that were honestly repeating a lot of the same code that was not the most necessary), I divided the program into Student, Session, Instructor, Schedule, and Main. This helped me better organize my train of thought and I think I spent a lot more time planning out my thought process before actually writing out the code.

The Student class became responsible for storing each student’s ID, name, email, and five ranked choices. One important change I made was using an array for the choices instead of separate variables like choice1, choice2, etc. At first, this felt less straightforward, but I realized it made the scheduling process much easier because I could loop through all five choices. This way I used less redundant code. The Session class stores the session ID, session name, instructor, and popularity information. The Instructor class groups sessions by instructor, which helps make sure the same instructor is not scheduled twice at the same time. These three classes felt quite similar when I was coding them with the same overall logic, just slight changes in variables and also the actual scanning in of CSV files. The Schedule class became the most complicated class because it actually places sessions into rooms and time slots, assigns students, checks capacities, avoids repeated sessions, and counts conflicts (it was also my longest chunk of code. Finally, the Main class was where I tied everything together by calling all the previously made methods.

I did end up reorganizing my CSV file into two separate ones that had less columns which made it easier for me to verify the correct data was being scanned in, and also a lot easier for me to read.

Working with multiple classes was one of the biggest challenges because small naming inconsistencies caused a lot of errors. For example, I had to make sure that if one class called getInstructor(), the Session class actually had a method with that exact name. I also had to make sure my data encapsulation worked accurately and I wasn't trying to access private methods or variables from other classes. I also learned that using consistent variable names matters a lot, especially when several classes are tied to each other. I did have some errors related to inconsistencies across classes that might have been a simple fix, but seemed a lot more complex because they involved much more code (more classes).

I also spent a lot of time debugging. Some errors were simple spelling mistakes, like typing intput instead of input, while others were harder to understand, like the NoSuchMethodError from an old compiled .class file. I learned that sometimes the source code can look correct, but the computer may still be running an older compiled version, so deleting old .class files and recompiling everything can fix the issue. I also fixed formatting problems in the output, especially when I tried using printf (in an attempt to use a fancier formatting style) and realized that the formatting was more confusing than helpful for this project. I ended up switching to the simpler println statements made the code easier to understand and debug.

Another major improvement was the output. At first, the program printed too much information in a messy way, which made it hard to tell whether the schedule actually worked. I changed the output so it now shows the most important parts: a schedule summary with total conflicts and conflicts per student, a session grid organized by time slot and room, a speaker schedule organized by instructor, and student schedules that list what each student should attend.
